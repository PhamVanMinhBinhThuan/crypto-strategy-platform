# Feature Specification: News and Sentiment

**Feature Branch**: `feature/008-news-sentiment`

**Feature ID**: `F-008`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "Implement Java-owned English News collection and a separate Python/FastAPI English Sentiment Analysis service using the Multi-channel LSTM-CNN architecture, with durable asynchronous orchestration, resilience, public analysis states, and shared contract verification. English text is analyzed natively without translation."

## Clarifications

### Session 2026-08-30

- Q: What artifact policy should F-008 require when the trained English model weights or matching English tokenizer are unavailable? → A: Bundle a pinned, versioned model and exact frozen tokenizer/vocabulary; expose liveness while loading, but treat a missing/incompatible artifact as terminal startup failure and exit nonzero for supervisor replacement; never train or download artifacts at startup.
- Q: Should Java require Python to analyze with an explicitly requested model release and echo all contract/provenance fields using canonical decimal strings? → A: Java sends the contract version and expected model name, model version, and preprocessing version; Python must echo exact matches or reject the request as non-retryable, and confidence/polarity use canonical decimal strings.
- Q: How should the service handle the model's potentially expensive initialization before accepting analysis requests? → A: Serve liveness first, lazily import TensorFlow/Keras inside one off-event-loop startup loader, remain not ready until warm-up, reject pre-ready analysis without reinitializing, and exit nonzero on terminal failure or the configurable 120-second default deadline.
- Q: Which default timeout and retry profile should govern one News Item's analysis for a specific model release? → A: Use a 2-second connect timeout, one 30-second TimeLimiter response deadline, three conservative Worker dispatch reservations with asynchronous 5-second and 30-second retry delays, a 120-second lease, and a per-Worker circuit breaker that opens for 30 seconds after at least 10 calls when 50% fail; the HTTP client has no blocking retry loop, and pre-dispatch readiness/concurrency/circuit rejections consume no reservation.
- Q: Which PostgreSQL constraint policy should the forward migration enforce for immutable Sentiment Results? → A: Preserve ADR-0008's unique `news_item_id + content_hash + model_version` result identity, introduce `news.sentiment_model_release` keyed by `model_version` for exact release provenance, and enforce parent content-hash equality, label/score ranges, foreign-key integrity, and accepted-result/release immutability in PostgreSQL.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Collect Trustworthy Canonical News (Priority: P1)

As a platform user, I want crypto news from configured sources to be collected, normalized, and shown once so that I can review relevant information without duplicate articles or unsafe provider content.

**Why this priority**: Canonical persisted News is the durable input for every sentiment and user-facing News flow. Sentiment cannot be reliable if collection identity, text, and publication time are unstable.

**Independent Test**: Feed deterministic provider fixtures containing valid articles, duplicate URLs, HTML, scripts, reordered records, and malformed records; verify that Java produces one safe canonical News Item per canonical URL, preserves valid publication provenance, and makes accepted News visible without running the Sentiment service.

**Acceptance Scenarios**:

1. **Given** a valid article from a configured provider, **When** collection runs, **Then** one canonical News Item is stored with stable identity, source, canonical URL, normalized title and content, publication and crawl instants, content hash, language, and `PENDING` analysis status.
2. **Given** two provider records that resolve to the same canonical URL, **When** they are processed concurrently or repeatedly, **Then** exactly one logical News Item exists and no previously accepted content is silently overwritten.
3. **Given** article content containing HTML markup, executable script, tracking markup, or unsafe control characters, **When** Java normalizes the article, **Then** the stored and analyzed text is sanitized, bounded, deterministic plain text and no executable content crosses the sentiment boundary.
4. **Given** an invalid URL, missing required title, invalid publication time, unsupported language, or unusable content, **When** collection processes the record, **Then** it is rejected or safely classified according to the published provider error rules without creating a partial accepted News Item.
5. **Given** the Sentiment service is unavailable, **When** a valid article is collected, **Then** the News Item remains stored and visible with its current analysis state.

---

### User Story 2 - Analyze English News Without Blocking the Platform (Priority: P1)

As a platform user, I want English crypto news to receive a clear sentiment label and confidence after collection so that I can understand the model's native English assessment while continuing to use News and Market features during analysis delays or failures.

**Why this priority**: Sentiment analysis is the primary F-008 outcome, while isolation from the model runtime is the principal architectural driver of ADR-0008.

**Independent Test**: Persist pending English News fixtures, run a Worker against a contract-compatible fake Sentiment service, and verify native English input crosses the Java-Python boundary without translation, asynchronous transitions, validated results, idempotent persistence, conservative dispatch-attempt accounting including a crash after reservation but before network dispatch, bounded retry, expired-lease recovery, and degraded behavior without loading the real machine-learning model.

**Acceptance Scenarios**:

1. **Given** a pending English News Item, **When** a Worker acquires its durable lease and receives a valid inference response, **Then** its Java-normalized English title/content are sent unchanged to the native English model, one versioned Sentiment Result is stored, and the News Item becomes `ANALYZED` atomically.
2. **Given** the same `newsId`, content hash, and model version is delivered or analyzed more than once, **When** valid duplicate outcomes are saved, **Then** they resolve to one logical Sentiment Result and the News Item remains consistently analyzed.
3. **Given** a timeout, rate limit, temporary service error, or open circuit breaker, **When** analysis cannot complete, **Then** the item remains recoverable as `PENDING` or `FAILED_RETRYABLE`, News remains visible, and Market Data, public API health, and technical Backtest behavior continue independently.
4. **Given** a permanent invalid request or a transient failure that exhausts its configured attempt limit, **When** the failure is classified, **Then** the News Item becomes `FAILED`, its safe failure state is observable, and no unbounded retry loop occurs.
5. **Given** a Worker crashes while an item is `ANALYZING`, **When** its lease expires, **Then** another Worker can reclaim the same logical work without losing the News Item or creating duplicate Sentiment Results.
6. **Given** the Sentiment service returns a mismatched request or News identity, an unknown label, an out-of-range score, a blank version, or an invalid timestamp, **When** Java validates the response, **Then** the response is not persisted as a successful result and is classified through the analysis failure policy.
7. **Given** a previously unavailable Sentiment service becomes ready again, **When** the next eligible retry cycle runs, **Then** recoverable items can progress to `ANALYZED` without manual record repair.
8. **Given** a Worker has durably consumed an attempt immediately before dispatch but crashes before the HTTP client confirms dispatch, **When** the lease expires, **Then** the reservation remains consumed, the work is reclaimable within the remaining budget, and the number of actual outbound calls can never exceed the configured attempt limit.

### User Story 3 - Browse News by Trading Pair and Analysis State (Priority: P2)

As an authenticated platform user, I want to browse recent News for a Trading Pair and see whether each item is pending, analyzed, retryable, or failed so that missing sentiment is not mistaken for neutral sentiment.

**Why this priority**: News and Sentiment provide value only when their provenance and availability are understandable to users; explicit state also demonstrates failure isolation rather than hiding model outages.

**Independent Test**: Associate News fixtures with canonical Assets, query multiple Trading Pairs and analysis states through the Java boundary, and verify deterministic pagination, correct base/quote matching, exact sentiment values, and non-disclosing degraded output.

**Acceptance Scenarios**:

1. **Given** a News Item linked to the base Asset or quote Asset of a Trading Pair, **When** that pair is used as a News filter, **Then** the item is eligible for the result; an item linked to neither Asset is excluded.
2. **Given** an item linked to both Assets of a pair, **When** the pair is queried, **Then** the item appears once rather than once per asset association.
3. **Given** analyzed and unanalyzed News Items, **When** a user lists News through the default UI boundary, **Then** every item exposes its analysis status and analyzed items expose only label, confidence, and polarity score; model-release and content-hash provenance remains available only through protected internal/operator/audit boundaries.
4. **Given** a pending, retryable, or permanently failed item, **When** it is returned publicly, **Then** sentiment is absent and the explicit analysis state distinguishes the condition without exposing stack traces, internal service addresses, lease details, or secrets.
5. **Given** more News Items than fit on one page, **When** pages are requested, **Then** items are ordered by publication time descending with News identity as a stable tie-breaker, with no duplicate or skipped item across an unchanged dataset.

### User Story 4 - Operate and Replace the Sentiment Model Safely (Priority: P2)

As a maintainer, I want the English sentiment model to have a versioned, independently testable service contract and accurate readiness state so that the model can be deployed, diagnosed, and replaced without changing News ownership or other Java capabilities.

**Why this priority**: Independent model lifecycle and replaceability are the reasons for the Python service boundary, and model provenance is required for trustworthy historical results.

**Independent Test**: Run service tests with mocked inference and shared contract fixtures, exercise liveness/readiness before and after a model double is loaded, then deploy two single-release service configurations sequentially and verify that Java accepts each compatible release while retaining separate immutable results.

**Acceptance Scenarios**:

1. **Given** the Sentiment process is running but eager model loading, artifact validation, or warm-up is incomplete, **When** health is checked, **Then** liveness reports the process alive while readiness reports that analysis must not be routed to it; analysis is rejected without triggering initialization. If terminal loading failure or the startup deadline occurs, the process MUST report a safe terminal startup failure and exit nonzero so its supervisor can replace it.
2. **Given** a normalized English text request conforming to contract version 1, **When** the service is ready, **Then** it analyzes the English text directly without translation and returns the matching request and News identities, one supported label, bounded confidence and polarity values, model name/version, preprocessing version, and a UTC analysis instant.
3. **Given** malformed, oversized, unsupported-language, or unauthorized input, **When** the internal analysis boundary receives it, **Then** it rejects the request safely without fetching a URL, touching shared storage, or exposing model paths and stack traces.
4. **Given** the active model version changes through a sequential single-release deployment, **When** the same News content is analyzed by the new version, **Then** its per-release attempt budget starts independently, a new versioned result may be retained, and the previous result is not overwritten.
5. **Given** Java and Python use the same versioned request, response, and error fixtures, **When** their contract suites run, **Then** both runtimes agree on required fields, enum values, decimal ranges, timestamps, size limits, and compatibility rules.

### Edge Cases

- A provider changes its payload shape, returns items out of order, repeats a page, times out midway, or sends a different article under an already accepted URL.
- URLs differ only by a fragment, host letter case, default port, or configured tracking parameters; the versioned URL canonicalization rule must determine whether they are one logical article.
- The title is usable but content is absent, or the normalized title/content becomes empty after sanitization.
- Two workers attempt to acquire the same pending item, or an old worker returns after its lease expired and a new worker completed the item.
- A lease expiry occurs while an inference response is in flight.
- Java content normalization changes and produces a new content hash for an existing logical URL.
- The service returns a valid result after the item's content hash has changed.
- The service is live but not ready, repeatedly returns `429`, exceeds the response timeout, or opens the circuit breaker while many items are pending.
- A result is numerically at exactly `0`, `1`, or `-1`, or contains a binary floating-point representation that cannot be accepted as an exact boundary decimal.
- The model produces probabilities that require a tie or neutral-label mapping; the versioned inference mapping must resolve it deterministically.
- A News Item is associated with the same Asset more than once or with both Assets in a Trading Pair.
- A pair contains a common quote Asset such as USDT; filtering semantics remain base-or-quote matching and may return quote-related News.
- Retention removes licensed article content while immutable metadata, hashes, Sentiment Results, or Experiment-referenced provenance must remain protected.
- Service credentials, article bodies, model file paths, provider payloads, database errors, or stack traces are accidentally included in logs or public errors.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: F-008 MUST establish `modules/news` as the single capability owner of canonical News Items, News provider contracts, analysis lifecycle, Sentiment Results, and the output ports used to persist them.
- **FR-002**: A canonical News Item MUST contain `newsId` as a typed News identity, nonblank source, canonical nonblank URL, normalized nonblank title, normalized analysis content, language, publication instant, crawl instant, content hash, and analysis status.
- **FR-003**: News identity MUST use the project's typed uppercase ULID convention, and all times crossing boundaries MUST represent UTC instants.
- **FR-004**: Java MUST own provider retrieval, provider error translation, URL canonicalization, HTML/script sanitization, whitespace and text normalization, content-size enforcement, content hashing, and News deduplication; provider-specific models MUST NOT cross the News provider adapter.
- **FR-005**: Logical News uniqueness MUST be the canonical URL. Repeated or concurrent collection of the same canonical URL MUST NOT create a second logical News Item.
- **FR-006**: A versioned canonicalization rule MUST define the exact normalized title, content, language, separators, character encoding, and URL representation used to calculate `contentHash`; equivalent normalized input MUST produce the same `sha256:` hash.
- **FR-007**: A conflicting provider record for an accepted canonical URL MUST NOT silently overwrite accepted content or provenance; the conflict MUST be idempotently recognized or reported through a stable News integrity error.
- **FR-008**: F-008 MUST support native English (`en`) analysis input. Java MUST send its normalized English title/content directly to the English model without translation or an intermediate language service. Any additional language MUST be explicitly configured and supported by a compatible model contract; unsupported languages MUST NOT be sent to the English model.
- **FR-009**: Accepted News MUST be durably visible independently of Sentiment service availability and MUST enter analysis as `PENDING` unless a valid result for the same content/model identity is already present.
- **FR-010**: Related News Assets MUST use existing canonical Asset identities and the existing News-to-Asset relation; duplicate News-to-Asset associations MUST collapse to one association.
- **FR-011**: Filtering News by a canonical Trading Pair MUST resolve that pair's base and quote Assets and include a News Item linked to at least one of them; an item linked to both MUST appear only once.
- **FR-012**: Related-asset relevance, extraction, or provider mapping MUST remain a News responsibility and MUST NOT grant News permission to modify Market Data-owned Asset or Trading Pair records.
- **FR-013**: The News capability MUST publish input use cases for collecting canonical News, acquiring/recovering analysis work, completing or failing analysis, and listing News with deterministic pagination and related-asset filtering.
- **FR-014**: The News capability MUST publish an output port for sentiment inference. Its HTTP adapter MUST be orchestrated and composed by `apps/worker`; News domain/application code MUST NOT depend on FastAPI, TensorFlow, Keras, HTTP client classes, or Python implementation details.
- **FR-015**: The Sentiment integration contract MUST be versioned as `sentiment-v1` and expose analysis at `POST /api/v1/sentiment/analyze`. Every request MUST include request identity, News identity, normalized title/content, language, content hash, `contractVersion`, and the exact expected `modelName`, `modelVersion`, and `preprocessingVersion`. A successful response MUST echo all identities and expected provenance exactly and return label, canonical exact confidence and polarity strings, and UTC analyzed time.
- **FR-016**: Sentiment labels MUST be exactly `POSITIVE`, `NEUTRAL`, or `NEGATIVE`; canonical confidence strings MUST represent a value in `[0,1]`; canonical polarity strings MUST represent a value in `[-1,1]`. Java MUST reject any response that violates identity, schema, canonical decimal form, range, expected provenance, language, timestamp, or content-hash expectations, and Python MUST reject a request whose expected contract/model/preprocessing release is not loaded.
- **FR-017**: The Python service MUST wrap a pinned English Multi-channel LSTM-CNN sentiment model behind the v1 contract, using a versioned converted model artifact and its exact frozen English tokenizer/vocabulary artifact with preprocessing version `multichannel-whitespace-en-1`, and MUST apply a documented, deterministic, versioned preprocessing and output-label mapping. It MUST NOT reconstruct the vocabulary from runtime input or translate input text.
- **FR-018**: Python MUST receive only Java-normalized text and metadata, perform model-specific preprocessing and inference, and return an inference result. It MUST NOT crawl News, fetch request URLs, call Binance, determine Strategy signals, or read/write PostgreSQL, Supabase, Redis, or Java internal state.
- **FR-019**: The Python service MUST be stateless between analysis requests except for read-only loaded model/tokenizer artifacts and process-level operational metrics.
- **FR-020**: The Python service MUST expose `GET /health/live` before importing TensorFlow/Keras or loading model artifacts, then lazily import TensorFlow/Keras only inside exactly one off-event-loop startup loader that validates and warms the pinned model and tokenizer/vocabulary. It MUST expose `GET /health/ready` for artifact and inference readiness, remain live but not ready while loading, reject analysis without triggering another initialization before readiness, and use a configurable startup deadline defaulting to 120 seconds. A terminal artifact/load/warm-up failure or deadline expiry MUST record a safe terminal state and cause nonzero process exit; a timed-out loader MUST NOT later publish readiness, and the supervisor MUST replace the process rather than leaving a live process with an unbounded model-loading thread.
- **FR-021**: The internal sentiment boundary MUST be inaccessible to browsers, MUST use environment-supplied service authentication where the deployment environment requires it, MUST enforce request/body/text limits, and MUST return safe errors without internal paths, class names, secrets, or stack traces.
- **FR-022**: Analysis MUST run asynchronously outside the Market Dashboard and public News request path with at-least-once delivery semantics; the system MUST NOT assume exactly-once execution.
- **FR-023**: F-008 MUST use a News-owned durable lease model rather than reusing the Experiment Search/Backtest Job aggregate. Durable work state MUST survive Worker, queue/cache, and Sentiment service restarts.
- **FR-024**: A new reviewed forward migration MUST extend `news.news_item` with canonical language, lease owner, lease expiry, nonnegative attempt count, and next-eligible-attempt data sufficient to reclaim crashed `ANALYZING` work and enforce bounded retry. Lease owner and expiry MUST be set and cleared consistently.
- **FR-025**: The forward migration MUST expand analysis status to include `FAILED_RETRYABLE`. Supported transitions MUST include `PENDING -> ANALYZING -> ANALYZED`, `ANALYZING -> FAILED_RETRYABLE -> ANALYZING`, and `ANALYZING|FAILED_RETRYABLE -> FAILED`; expired `ANALYZING` leases MUST be reclaimable.
- **FR-026**: Acquiring a lease and validating eligibility MUST be atomic. After readiness and local admission permit execution, the Worker MUST atomically consume one conservative dispatch-attempt reservation immediately before network dispatch. Completing an analysis MUST atomically persist or resolve the idempotent Sentiment Result, mark the matching News content `ANALYZED`, and clear lease/retry fields.
- **FR-027**: A stale Worker whose lease expired or whose content hash no longer matches MUST NOT overwrite the state or result accepted by the current lease holder.
- **FR-028**: The logical and PostgreSQL-enforced idempotency key for an accepted result MUST remain `newsId + contentHash + modelVersion` as defined by ADR-0008; duplicate processing MUST produce at most one stored logical result for that key. `modelVersion` MUST reference exactly one persisted Sentiment Model Release.
- **FR-029**: Changing normalized content or model version MUST permit a distinct result and MUST NOT overwrite a result retained for audit or future Experiment provenance.
- **FR-030**: Every persisted Sentiment Result MUST retain nonblank language, model-version reference, and content hash plus a supported label, exact confidence in `[0,1]`, exact polarity in `[-1,1]`, and analyzed time. Its model name, preprocessing version, and contract version MUST resolve through the referenced immutable Sentiment Model Release rather than being duplicated on each result.
- **FR-031**: A new forward migration MUST introduce `news.sentiment_model_release` with `model_version` as its primary key and required nonblank `model_name`, `preprocessing_version`, and `contract_version` columns. The existing `news.sentiment_result.model_version` column MUST become a foreign key to that release table while preserving the baseline unique constraint on `(news_item_id, content_hash, model_version)` and existing label/score range checks. The migration MUST add required result-language and release-integrity constraints, preserve existing baseline data safely, and leave both already applied migrations unchanged.
- **FR-032**: F-008 MUST define how legacy baseline Sentiment rows receive explicit compatible provenance during migration; migration MUST abort rather than invent conflicting provenance when safe deterministic backfill is impossible.
- **FR-033**: PostgreSQL MUST reject insertion of a Sentiment Result whose content hash differs from its parent News Item, reject a result whose model version has no release row, reject mutation or deletion of an accepted Sentiment Result, and reject mutation or deletion of an established Sentiment Model Release in a way that could change or orphan result provenance. Concurrent operations MUST use the global lock order `Sentiment Model Release -> News Item ordered by News ID -> Sentiment Result -> News Item Asset ordered by Asset ID`; release registration/verification MUST finish in its own short transaction before News work is claimed. SQL deadlock or serialization failures (`40P01`/`40001`) MUST become bounded recoverable persistence outcomes rather than unbounded in-transaction retries. This enforcement MUST be introduced only through the new forward migration.
- **FR-034**: The Java Sentiment HTTP client MUST have environment-configurable connection and response timeouts, concurrent-inference limits, and Resilience4j `CircuitBreaker` and `TimeLimiter` protection only. It MUST NOT configure or execute an internal Resilience4j Retry, blocking sleep, or synchronous retry loop. Defaults MUST be a 2-second connection timeout, one 30-second TimeLimiter-owned end-to-end response deadline, three conservative dispatch-attempt reservations per `newsId + contentHash + expected model release`, asynchronous retry delays of 5 then 30 seconds, and a 120-second lease. Circuit state and concurrency limits MUST be per Worker process; aggregate capacity is the configured per-process limit multiplied by the number of Worker replicas. Each admitted leased execution MUST make at most one outbound inference call.
- **FR-035**: Circuit accounting MUST follow this matrix exactly: cached/probed not-ready, no claimed work after readiness preflight, unavailable local concurrency, open-circuit rejection, and half-open permit rejection occur before dispatch, consume no attempt, and record neither circuit success nor failure; stale/database-rejected attempt start after a circuit permit was admitted consumes no attempt and explicitly releases that permit as unused; a valid compatible `2xx` records circuit success; connection failure, the TimeLimiter deadline, dispatched `429`, dispatched `503 NOT_READY`, and eligible `5xx` record one circuit failure and are transient; malformed/oversized/mismatched or otherwise invalid `2xx` records one circuit failure but is permanent for that unchanged item/release; authentication, unsupported language/release, invalid unchanged input, and other permanent `4xx` are ignored by circuit metrics and fail the item without retry; persistence failure after a valid HTTP response does not change the already-recorded circuit success. Each admitted circuit permission MUST receive exactly one success, failure, or explicit unused-permit release; a timed-out/cancelled future's late completion MUST be ignored. `Retry-After` MAY move persisted eligibility later but MUST NOT block or increase the attempt limit.
- **FR-036**: The Worker MUST exclusively orchestrate bounded exponential-backoff retry asynchronously. A persisted `attempt_count` value is a conservative dispatch reservation consumed atomically after readiness/concurrency/circuit admission and immediately before handing the request to the HTTP transport. A crash in the unavoidable reservation-to-network window leaves the reservation consumed even when no packet can be proven to have left; therefore actual outbound calls MUST be less than or equal to the configured reservation limit. After a transient failure with remaining budget, the Worker MUST transition the leased item to `FAILED_RETRYABLE`, persist a future `nextEligibleAttempt` using the applicable 5- or 30-second delay, and release the lease; a later acquisition performs one new reservation/call. Pre-dispatch readiness, concurrency, or circuit rejection MUST schedule future eligibility without consuming a reservation. Exhausted or permanent failure MUST leave the item `FAILED`.
- **FR-037**: Each Worker process MUST own an independent circuit breaker with a 50% failure-rate threshold after at least 10 recorded calls and a 30-second open interval by default. The Worker MUST perform a readiness preflight that is not decorated by the inference circuit, claim at most a bounded configurable batch ordered by effective eligibility instant ascending and then News ID ascending, acquire local concurrency and circuit permission, consume the attempt reservation, and dispatch. No-work cycles end before circuit acquisition; if attempt start is rejected after a half-open permit is acquired, the permit MUST be released as unused. When open, the Worker MUST schedule eligibility no earlier than the remaining/default open interval without consuming an attempt or entering a tight loop; other capabilities continue independently.
- **FR-038**: Correlation identity and News identity MUST propagate through Worker lease processing and Java-to-Python calls and appear in safe structured logs. Full article content and credentials MUST NOT be logged by default.
- **FR-039**: The public News API MUST retain the existing `GET /news-items` boundary, authenticated Java access, newest-first ordering, stable ID tie-breaking, bounded cursor pagination, and optional Trading Pair filtering.
- **FR-040**: The default public News API used by the UI MUST expose only `analysisStatus` and, for an analyzed item, the lightweight sentiment fields `label`, `confidence`, and `polarityScore`. It MUST NOT expose `modelName`, `modelVersion`, `preprocessingVersion`, `contractVersion`, or `contentHash`; those provenance fields MUST remain available only through separately protected internal/operator/audit boundaries. Non-analyzed states MUST expose no fabricated or stale sentiment and MUST NOT treat missing sentiment as `NEUTRAL`.
- **FR-041**: Public responses MAY expose a safe stable failure category or degraded indicator but MUST NOT expose lease owner, retry internals, service credentials, internal network locations, provider bodies, model paths, SQL details, or stack traces.
- **FR-042**: Confidence and polarity MUST use canonical decimal-string serialization across the Java-Python contract, shared fixtures, and public boundary, and exact decimal semantics in Java and persistence; binary floating-point types MUST NOT cross Java public capability boundaries.
- **FR-043**: Shared versioned JSON Schema or equivalent contract artifacts and identical valid/invalid JSON fixtures MUST verify the analysis request, success response, safe error response, health response, enum, range, timestamp, size, and compatibility rules in both Java and Python.
- **FR-044**: Java tests MUST verify timeout, bounded retry, non-retryable failure, the full circuit outcome matrix, permit release, per-Worker concurrency, circuit opening/recovery, invalid response rejection, lease expiry/reclaim, the crash after attempt reservation but before network dispatch, stale completion, concurrent release registration, deadlock/serialization translation, and idempotent result persistence. MockWebServer tests MUST use deterministic Dispatchers, barriers/latches, controlled executors, and explicit circuit transitions; they MUST NOT use wall-clock sleeps, unreachable-host timing, or load the Python model.
- **FR-045**: Python unit and contract tests MUST replace model inference with a fast deterministic test double while verifying preprocessing invocation, label mapping, response validation, health transitions, request limits, and safe errors. Default tests MUST inject Clock/ID/executor dependencies, coordinate concurrency with events rather than sleeps, and prove TensorFlow/Keras is not imported before the off-event-loop loader is invoked.
- **FR-046**: Default repository verification MUST remain deterministic, fast, secret-free, and independent of external News providers and mutable model downloads. Startup MUST NOT train, rebuild a vocabulary, or download artifacts. Release acceptance, however, MUST produce an approved immutable model/tokenizer bundle, store it in the approved artifact location, pin its digest plus model/preprocessing/contract versions in deployment configuration, and run an environment-gated cold-start smoke test from process launch through liveness and readiness within the 120-second default deadline.
- **FR-047**: F-008 MUST provide evidence that stopping or timing out the Sentiment service does not interrupt Market Data, public API liveness, News visibility, or technical Backtest behavior and that degraded analysis state becomes observable within the architecture quality target.
- **FR-048**: News and Sentiment metrics MUST cover collection acceptance/rejection/duplicates, pending/analyzing/retryable/failed counts, lease recovery, request count, latency, timeout/retry, circuit state, label counts, active model/preprocessing versions, model load time, and readiness; label distribution MUST NOT be presented as model-accuracy evidence.
- **FR-049**: News content retention MUST respect provider licensing and the baseline maximum-retention assumption. Cleanup policy implementation is outside F-008 unless separately specified, and retention MUST NOT delete immutable provenance referenced for reproducibility.
- **FR-050**: F-008 MUST NOT implement Sentiment Strategy, StrategyContext changes, Experiment/Backtest integration, historical sentiment dataset freezing, Search/Leaderboard behavior, real trading, wallet/order behavior, or direct browser access to Python or business tables.
- **FR-051**: F-008 MUST NOT add an unrelated generic HTTP/client utility outside the News capability. Any HTTP transport implementation introduced for News providers or Sentiment MUST remain behind News-owned contracts and must not expose provider or framework types.
- **FR-052**: The implementation MUST use the existing Java 21/Spring Boot 3 foundation for Java runtimes and a standalone Python 3/FastAPI service with pinned Keras/TensorFlow and model dependencies. Dependency/model licensing and artifact provenance MUST be reviewed before distribution; F-008 MUST NOT be considered release-ready until the deployable single-release model bundle is produced, digest-pinned, and its cold-start smoke evidence is recorded. Model replacement occurs through sequential single-release process deployments, not concurrent multi-model serving inside one process.
- **FR-053**: All affected acceptance, contract, persistence, architecture, resilience, failure-recovery, and security scenarios MUST have reproducible evidence. Evidence MUST remain `Planned` until produced by an actual test or review result.
- **FR-054**: F-008 MUST allow multiple configured News providers to implement the same `NewsProvider` port independently, without changing canonical News domain or application logic.

### Key Entities

- **News Item**: Java-owned canonical article with stable typed identity, canonical URL, safe normalized title/content, language, content hash, source, publication/crawl provenance, related Assets, analysis state, and durable lease/retry metadata.
- **News Provider Record**: Untrusted source-specific representation accepted only by a provider adapter and never exposed as a domain or public contract.
- **Related Asset**: Association between one News Item and an existing Market Data-owned Asset, with optional bounded relevance; used to derive Trading Pair filters without transferring Asset ownership.
- **Analysis Lease**: Time-bounded exclusive claim by a Worker for one eligible News Item, including owner, expiry, attempt count, and next eligible attempt; it is coordination state, not an Experiment Job.
- **Sentiment Analysis Request**: Versioned internal message containing correlation/request identity, News identity, normalized title/content, language, and content hash.
- **Sentiment Model Release**: Immutable persisted reference keyed by model version and bound to exactly one model name, preprocessing version, and sentiment contract version; changing any member requires a new release row with a new model version.
- **Sentiment Result**: Immutable Java-owned model outcome uniquely identified logically by News identity, content hash, and model-version foreign key, with language, label, exact scores, and analyzed instant; full release provenance resolves through Sentiment Model Release.
- **Model Runtime State**: Operational liveness/readiness and active model metadata maintained by the stateless Python process; it is not durable News business state.
- **Analysis Availability**: Safe user/operator-facing representation of whether analysis is pending, active, retryable, complete, permanently failed, or temporarily degraded.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Across duplicate, reordered, and concurrent collection fixtures, 100% of records resolving to the same canonical URL produce exactly one logical News Item and no accepted article is silently overwritten.
- **SC-002**: Across all sanitization fixtures, 100% of accepted titles and content contain no executable HTML/script content, produce the expected versioned content hash, and yield identical canonical output on repeated processing.
- **SC-003**: In failure-isolation verification, stopping or timing out sentiment analysis causes zero failed Market Data health checks, zero interrupted technical Backtest fixtures, and zero loss of accepted News; degraded analysis state is observable within five seconds.
- **SC-004**: In duplicate-delivery and concurrent-Worker verification, each `newsId + contentHash + modelVersion` produces at most one logical Sentiment Result, including after at least three deliveries, a crash/reclaim sequence, and a crash after a persisted attempt reservation but before provable network dispatch.
- **SC-005**: Every expired analysis lease fixture is reclaimable by another Worker, while 100% of stale completions are rejected from overwriting the current item state or accepted result.
- **SC-006**: All invalid response fixtures—identity/hash mismatch, unknown label, out-of-range decimal, missing provenance, malformed timestamp, oversized body, and incompatible contract—are rejected with no successful Sentiment Result persisted.
- **SC-007**: Transient and crash-window fixtures never exceed three persisted dispatch-attempt reservations or three actual outbound calls under the default profile; a reservation without a provable call remains consumed. Retryable failures use 5- and 30-second eligibility, permanent failures receive no automatic retry, and pre-dispatch readiness/concurrency/circuit rejections consume zero reservations and produce no tight loop.
- **SC-008**: After analysis availability returns, every retryable fixture becomes eligible again and reaches `ANALYZED` within one configured retry cycle without manual database repair.
- **SC-009**: Java and Python contract suites accept 100% of shared valid fixtures and reject 100% of shared invalid fixtures with the same identity, canonical decimal, enum, range, timestamp, expected-provenance, and compatibility interpretation.
- **SC-010**: Default Java verification performs zero real model loads and default Python unit/contract verification performs zero real external provider calls or mutable model downloads.
- **SC-011**: For every News query fixture, pair filtering includes items linked to either base or quote Asset, excludes unrelated items, returns a dual-linked item once, and produces deterministic pagination without duplicates or omissions.
- **SC-012**: Public News representations distinguish all supported analysis states in 100% of fixtures; no pending, retryable, or failed item is represented as neutral sentiment.
- **SC-013**: Re-analyzing fixed content through two sequential single-release deployments preserves two immutable versioned outcomes, resets the persisted attempt budget for the new target release, and leaves the earlier outcome byte-equivalent under the published canonical result encoding.
- **SC-014**: Security verification finds zero Python database/Redis access paths, zero Python URL fetches from analysis input, zero browser-to-Python paths, and zero secrets, full article bodies, internal paths, SQL details, or stack traces in public errors and default logs.
- **SC-015**: Architecture verification finds zero News-domain dependencies on Java HTTP/framework clients, Python implementation classes, persistence implementation, Market Data internals, Strategy, Backtest, Search, Evaluation, or Leaderboard.
- **SC-016**: In deterministic fake-runtime and real pinned English-bundle cold-start verification, liveness becomes available before TensorFlow/Keras import and artifact loading, 100% of pre-warm-up English analysis requests are rejected without triggering another load, readiness succeeds only after one validated English-model warm-up, and a terminal failure or exceeded 120-second default deadline exits nonzero and can never later report ready.
- **SC-017**: PostgreSQL verification rejects 100% of duplicate ADR identity, duplicate/conflicting model-release identity, orphan model-version reference, parent-hash mismatch, invalid label/range, blank release provenance, accepted-result mutation/deletion, and established-release mutation/deletion fixtures. Concurrent verification MUST cover identical/conflicting runtime release registration, deterministic batch claims, the global lock order, and bounded recoverable translation of forced `40P01`/`40001` outcomes without an unbounded database retry loop.
- **SC-018**: The same News provider contract suite passes for at least two independently configured provider implementations, and adding the second requires zero changes to canonical News domain/application behavior.

## Assumptions

- F-003 Market Data/Dataset and F-004 Strategy capabilities are present and remain unchanged except where composition must expose existing canonical Asset/Trading Pair queries through public boundaries.
- ADR-0008 is accepted and authoritative: Java owns News and durable Sentiment Results; Python owns only stateless model inference.
- The existing `news.news_item`, `news.news_item_asset`, and `news.sentiment_result` baseline tables are retained. Schema gaps are corrected only through one or more new reviewed forward migrations; existing migrations are never edited or remotely applied as part of specification work.
- The durable lease approach is sufficient for F-008 analysis scheduling and crash recovery. Redis delivery or Outbox publication may be added later behind the same News work contract, but Redis is not required to be the source of analysis truth.
- `attempt_count` is a conservative dispatch reservation rather than proof that a packet reached Python. The reservation is consumed before transport handoff; a crash in that window does not restore it, which preserves the hard upper bound on actual outbound calls.
- `FAILED_RETRYABLE` is a durable business state. Immediate transient failures are scheduled using a persisted next-eligible-attempt instant; retry thresholds and delays vary by environment.
- Circuit breaker state and concurrency admission are local to each Worker process. Deployment capacity planning accounts for the number of Worker replicas; no distributed circuit breaker is introduced.
- Pair filtering deliberately uses base-or-quote Asset matching. This may include broad quote-asset News and can be refined only through a later product requirement without changing Asset ownership.
- English (`en`) is the required analysis language for the initial model. Other languages may remain stored and visible but are not analyzed unless a compatible explicitly versioned model is configured. F-008 contains no translation layer.
- The referenced [Multi-channel LSTM-CNN repository](https://github.com/ntienhuy/MultiChannel) supplies training code and datasets but not a deployable trained-weight and serialized-tokenizer pair. F-008 therefore depends on producing and packaging a pinned, converted model artifact with its exact frozen tokenizer/vocabulary; planning must verify license, supported dependency versions, reproducible artifact provenance, label set, checksum validation, and safe packaging.
- Each Python process loads exactly one model release. Replacing the active release uses a sequential deployment and restart; simultaneous multi-model serving is outside F-008.
- The three-label and polarity mapping is part of the versioned preprocessing/inference contract. If the upstream artifact does not natively emit all required values, planning must define and fixture-test a deterministic mapping without claiming unverified model accuracy.
- Existing public authentication and correlation conventions from the Java foundation are reused. News is shared data, but browser reads continue through the authenticated Java API.
- Article content retention depends on provider licensing and is at most 30 days when the baseline assumption applies. A later maintenance feature owns automated cleanup; immutable hashes/results and referenced reproducibility evidence remain protected.
- Model-quality benchmarking, financial interpretation, Sentiment Strategy, and Experiment/Backtest use of sentiment are outside F-008.
