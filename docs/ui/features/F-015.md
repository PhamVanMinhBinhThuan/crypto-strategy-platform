# F-015 UI Reference Mapping

## Feature

F-015 extends the Search & Leaderboard surface with an authoritative configurable composite-search workflow and bounded Worker execution.

## UI-04 — Search & Leaderboard

- Screenshot: `../screens/Search & Leaderboard.png`
- Prototype page: `../prototype/pages/SearchLeaderboardPage.tsx`
- Prototype components: `../prototype/components/search/`
- Production routes: `/search` and `/search/{experimentId}`

## Required configuration flow

1. Select pair, timeframe, Start UTC and End UTC.
2. Create a Binance-backed frozen dataset or select an existing immutable snapshot by provenance.
3. Configure simulated initial capital, transaction fee and slippage shared by every Candidate Backtest.
4. Select the eligible Strategy pool and edit typed parameter domains for each selected Strategy version.
5. Set minimum/maximum component counts and Majority Vote 1.0.0.
6. Select a generator from the server catalog, its version and seed.
7. Set candidate/duration stop bounds, Worker concurrency and Top-K.
8. Review cardinality, start Search and navigate to `/search/{experimentId}`.

## Runtime presentation

- The configuration form never accepts a raw dataset ID.
- Capital is explicitly labeled as simulated quote-asset capital, not a Binance wallet balance. Fee and slippage are entered as percentages and sent as exact decimal rates.
- Provider access happens only while creating a frozen dataset. Every Candidate Backtest reads the selected stored snapshot.
- Top-K controls retained Leaderboard rows; it does not control candidate budget or the in-flight window.
- Progress is aggregate and authoritative: allocated, active, completed, failed, remaining and terminal reason.
- A Candidate is a composite definition containing exact component Strategy versions, per-component parameters and combination policy.
- REST snapshots remain authoritative; realtime messages only improve freshness.

## Prototype boundaries

The prototype supplies visual hierarchy only. Its single “current candidate”, Worker animation and example Leaderboard values are not runtime behavior and must not be copied as browser-side simulation. Production metrics, rankings and lifecycle states come from released APIs.

## Required states

Configuration, monitor and Leaderboard must cover loading, empty, validation error, dependency unavailable, active, stopping, stopped, exhausted, failed and completed states. Fixture data remains explicitly labeled and follows the same public request shapes.
